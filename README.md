# System One Model 实践探索

探索 Laya、Jev、Kev 在国内中文任务中的适用场景和能力边界。先用游戏做可控对照：模型提出结构化选择，游戏规则决定能否执行。

## 游戏：已得到的结论

- **贪吃蛇，十种子配对：**本地 Laya 与远程 Jev 都是 10/10 通关。Jev 总步数少 **5.42%**，后端整批耗时多 **48.3%**；Jev 仅在 6/10 个 seed 领先，尚不能认定稳定更省步。给定规划器安全候选后的已证最短原选率为 Laya **99.47%**、Jev **100%**，不是模型独立寻路正确率。[逐种子数据](docs/results/snake-2026-09-23.md)
- **Kev-0.8B，补充实测：**同一预设 seed 的单局十关通关，2,253 步、429/429 次已证最短原选及采纳；请求延迟中位数 **954 ms**。另有两局旧完整对局。它们使用不同代码快照或缺少批次记录，不能与 Laya/Jev 十局组成三模型排名。[Kev 逐局数据](docs/results/kev-0.8b-2026-09-24.md)
- **象棋，Pikafish 参照：**Laya 历史自对弈的 101 次非强制选择中，**19 次**与引擎首选一致，**29 次**被守门采纳。Kev 在相同 101 个保存局面上 **95 次**选中首选，但题目明确标出了首选；这主要衡量遵循给定排序，不能当成棋力或真实对局采纳率。[象棋结果与口径](docs/results/xiangqi-2026-09-23.md)

贪吃蛇的存活依赖共同规划器，象棋候选与守门依赖 Pikafish。模型原选、实际执行和规则接管须分开统计；当前还没有三模型同代码、同条件的完整游戏排名。

## UI 交互

目前只在游戏界面验证模型切换、单步观察和原选／执行／守门记录。中文客服、表单等 UI 场景尚未实现，也没有选型结论。

## 其他中文场景

[Laya 的 48 条合成中文题](laya-zh/evaluation/results/REPORT.md)中，文档流程 `choice` 为 **14/16**，游戏高层选择为 **5/16**；样本小且未做业务校准，不能推断生产适配，更不能给 Jev/Kev 排名。后续需要同题中文标注集，分别测错误率、置信度、延迟和数据出端条件。
