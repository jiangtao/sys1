# System One Model 实践探索

本项目要回答的是：**Laya、Jev、Kev 这几种 System One Model，在国内中文任务中各自能稳定完成什么，边界在哪里，什么条件下值得接入。**我们先用游戏建立可控的真实交互，再逐步验证 UI 判断、文档流程和任务路由。每个“适合”的判断都要落到任务、输入分布、错误代价、延迟和部署约束上。

这里的 *System One* 指对 `state` 提出 `choice`、`score`、`noul` 等结构化问题并取得直接决策结果的接口形式，参见 [TypeSafe 官方 API 示例](https://docs.typesafe.ai/introduction/quickstart)。本仓库接入本地 Laya、远程 Jev、本地 Kev；**Jev 的推理发生在远程服务**。共同的接口让三个模型进入同一实验流程，效果仍需分别测量。

## 要回答的问题

- **中文任务边界**：口语、省略、否定、中文夹英文术语、数字与日期、长文档和相近选项会怎样影响 `choice`、`noul`、`score`？
- **场景适配**：哪些任务能由模型直接建议，哪些需要确定性规则、人工复核或保持现有流程？允许出网、端侧资源和响应时限会怎样改变选择？
- **可用概率**：高置信输出在本场景里是否真的更可靠？校准后的覆盖率、错误率与回退成本是多少？

“国内中文场景”在这里指实际中文输入及其业务、设备和数据流转条件；当前实验不能替代具体行业的验收。

## 游戏

两个游戏提供不同的决策节奏和验证条件：

| 游戏 | 模型参与的位置 | 确定性边界 | 主要观察问题 |
| --- | --- | --- | --- |
| [贪吃蛇](snake/README.md) | 每步从安全候选方向中提议下一步；十关逐步增加拥挤程度 | 规划器检查蛇身、存活和已证路线；必要时直接执行或接管 | 高频调用的延迟、上下文预算、模型改选与规划器贡献 |
| [象棋](xiangqi/README.md) | 从 Pikafish 提供的合法着法和 MultiPV 分支中选着 | 引擎检查合法性与评分；不满足等优条件的原选被守门 | 不同局面的候选判断、守门率、失败后的可重试性 |

### 已完成的游戏跑批

| 模型 | 通关 | 总步数 | 已证最短路线原选 | 原选采纳 | 请求延迟中位数 / P95 | 后端整批耗时 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 本地 Laya | 10/10 | 21,843 | 2,268/2,280（99.47%） | 2,268/2,280（99.47%） | 132.8 / 197.6 ms | 645.467 s |
| 远程 Jev 1.13 | 10/10 | 20,659 | 2,450/2,450（100%） | 2,450/2,450（100%） | 259.5 / 325.0 ms | 957.388 s |

Jev 累计少走 1,184 步（5.42%），在 6/10 个 seed 领先，但配对步数差的 95% 近似区间跨过零。Jev 这套远程部署的整批耗时多 48.3%；延迟包含网络，不能当作纯推理速度。“正确”仅指从**规划器给出的安全候选**中选中本颗食物的已证最短路线，通关主要受共同规划器保护。另组三种子消融中，纯规划器固定参考共 5,511 步，规划器加 Laya 为 4,972 步；后续单种子随机同长路线消融未证明 Laya 稳定优于随机平局策略。十种子报告绑定的是当日代码快照，当前 HEAD 尚未同配置复测。

### 三种模型的中文场景假设

| 模型 | 当前接入 | 优先验证的中文任务 | 首要边界 |
| --- | --- | --- | --- |
| [Laya](https://huggingface.co/convaiinnovations/laya-multilingual) | 本地部署的多语言模型，本项目用中文 | 高频、短输入的选项判断；不宜逐步发送远端的游戏或 UI 提示 | 原始概率需要按场景校准；有序评分、相近选项和复杂规则需要单独验证 |
| [Jev](https://docs.typesafe.ai/introduction/quickstart) | TypeSafe 托管 API | 允许远程调用的中文任务，作为同题参照；验证较长输入和复杂判断 | 数据出端、网络稳定性、调用成本；不能把远程服务的整体耗时当成模型推理耗时 |
| [Kev](https://github.com/jaredpalmer/kev) | 外部开源实现的本地 `kev-0.8b` 服务 | 需要本地运行、可检查实现或针对中文任务微调的低风险试验 | 已见单局延迟波动和明确标签下的高首选一致率；中文业务迁移、长上下文与独立对弈能力仍需测量 |

表中是**待验证的选型假设**，不是已经证实的三模型排名。[Laya 上游模型卡](https://huggingface.co/convaiinnovations/laya-multilingual)明确提示原始概率过置信、有序 `score` 较弱；[Kev 上游说明](https://github.com/jaredpalmer/kev#limitations)也列出校准、选项顺序和长上下文限制。这些上游结果只能帮助设计测试，不能直接当成本项目中文任务的成绩。

### 中文业务合成基线

本仓库的 [Laya 中文合成集](laya-zh/evaluation/results/REPORT.md)只有 48 条，Agent 调度、游戏高层决策、文档流程各 16 条。文档流程的 `choice` 命中率为 `0.875`，游戏高层决策为 `0.3125`，Agent 调度为 `0.5000`；整体 `score` 四舍五入准确率为 `0.3750`。这些数字显示同一模型在不同问题定义下差异很大，**不能视作生产精度或三模型对比**。

游戏实测与这组合成业务题属于不同数据集。仓库尚无 Jev、Kev 与 Laya 同题的中文业务评测；要回答三者分别适配什么中文场景，还需要共用中文任务集、统一候选与标注，并记录每种模型的原选、失败和守门结果。

### 怎样判定场景适配

每个候选场景先定义具体动作和误判代价，再用未参与调参的中文样本验收。样本应覆盖口语与正式书面语、行业词汇、中文夹英文、否定和冲突证据、长短上下文、相近选项与无法从输入判断的情况。

| 维度 | 同题记录 | 决定什么 |
| --- | --- | --- |
| 判断质量 | `choice` 命中与混淆、`noul` 错报/漏报、`score` 等级误差，按场景分层 | 哪些任务可以建议，哪些仍需规则或人工 |
| 置信度 | 校准误差、不同阈值下的覆盖率与覆盖集错误率 | 能否设置自动执行阈值，灰区有多大 |
| 稳健性 | 改写、选项顺序、超长输入、缺失关键证据时的答案变化 | 提示和输入应如何约束，何时拒答或回退 |
| 运行条件 | 目标设备上的 p50/p95 延迟、内存、失败率、远程调用量与数据出端范围 | 本地或远程部署是否符合该场景约束 |

游戏先验证这套方法；文档和任务路由需要各自的真实中文标注集，不能直接沿用游戏成绩。

### 实践与治理

1. **把建议和执行分开。** 同一步分别记录模型原选、规则校验、实际动作与接管原因。贪吃蛇的规划器、象棋的 Pikafish 都不能被算作模型自己的推理能力。
2. **让比较条件可复现。** 贪吃蛇固定 seed、关卡与候选；象棋固定 FEN、行棋方、候选和引擎搜索预算。分别统计原选采纳率、守门率、失败率、延迟与整局结果，不用一次通关或胜负替代逐步评估。
3. **明确不调用模型的步骤。** 唯一安全方向等确定性情形可以跳过模型，但须记录 `modelCalled=false`。比较调用量与正确率时把跳过、成功、失败和回退分开计算。
4. **失败要有可见的语义。** 贪吃蛇在已有已验证路线时可记录规划器接管，模型在开局前不可用则拒绝创建该模型的游戏；象棋的模型请求失败会保留当前回合并返回可重试错误，不静默冒充模型落子。界面和日志都应显示这些差别。
5. **版本、输入和置信度一起治理。** 固定模型 revision，记录输入预算与实际模型身份；跨 tokenizer 的 token 数不直接比较。概率或置信度只是模型输出，在本游戏局面上测量校准之前不作为自动执行阈值。
6. **保护运行数据。** 密钥留在仓库外；Laya/Kev 权重、对局与运行日志不提交 Git。收集对照记录时保留必要的状态、候选和结果，并区分本地与远程请求。

这套做法与 [NIST AI RMF 的测量与监控建议](https://airc.nist.gov/airmf-resources/playbook/measure/)一致：记录覆盖与干预，持续评估系统在实际场景中的行为。这里的具体阈值和策略仍由游戏实测决定。

## UI 交互

游戏界面是第一处交互实验：玩家可以切换模型、暂停或单步观察，并展开模型请求、原始响应、候选分支和最终执行。贪吃蛇区分模型建议与规划器接管；象棋显示模型原选、引擎守门和实际落子。展示“模型做了什么”也要展示“应用替它做了什么”，避免把守门后的结果归功于模型。

下一步可以在中文客服工作台、表单和信息流里验证提示优先级、操作建议或界面状态分流。它们**尚未在本仓库实现**；先让模型提出可撤回的建议，保留用户覆盖入口，再按本页的质量、延迟和数据流转指标决定采用本地或远程模型。

## 其他

结构化决策还可能用于 Agent 路由和文档流程。早期 [20 条脱敏任务路由评测](laya-zh/evaluation/sessions/results/REPORT.md)中，Laya 的完整角色集合仅匹配 `1/20`；这批样本和标签不足以评定三模型优劣，却已提醒我们不能让当前版本直接自动派发多个 Agent。文档流程的合成题也需把分类和风险评分分开验收。后续扩展会沿用游戏中的边界：固定输入与候选、保留原始选择、记录干预、让失败可恢复。
