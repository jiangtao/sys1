# Laya 应用场景与产品方向

本文记录当前中文部署可以承载的业务方向，以及仍需要在服务外层实现的调度和生产化能力。示例都基于当前已经存在的 `POST /v1/decide`，不代表服务已经直接接入游戏、文档系统或 SubAgent 调度器。

## 一页结论

Laya 适合做“本地/服务端实时结构化决策中间件”：把一段状态和一组明确的问题转换为可计算的选项、分数或真假判断。它不是生成式聊天模型，也不会直接生成长文本、执行工具或启动 SubAgent。

当前最值得优先验证的方向是：

1. Agent 调度与 AI 安全网关：在调用昂贵模型或工具前，先判断任务类型、风险和是否需要人工介入。
2. 文档外发安全与审批路由：判断文档是否敏感、是否需要法务/财务审核，再由业务系统执行拦截或流转。
3. 游戏 AI Director：由游戏服务器调用，判断 NPC 高层策略、动态难度和事件节奏，不参与每帧底层控制。

以上三项是产品方向；当前目录已经实现的是本地模型和 `POST /v1/decide`，阈值执行、身份认证、业务动作和外部系统连接尚未实现。

## 当前接口能表达什么

接口请求是：

```http
POST http://127.0.0.1:8765/v1/decide
Content-Type: application/json
```

请求体包含：

- `state`：字符串、JSON 对象或数组，描述当前业务状态。
- `questions`：问题字典；每个问题有 `type` 和 `instructions`，`choice`/`score` 还需要 `criteria`。

三种问题类型的含义：

| 类型 | 输出 | 适合的问题 |
| --- | --- | --- |
| `choice` | 选项、各选项 `probabilities`、`confidence` | 应交给哪个部门、NPC 采取什么策略、文档属于什么类型 |
| `score` | 有序等级的期望 `score`、各等级概率和 `legend` | 紧急度、风险等级、难度等级 |
| `noul` | `noul` 真假概率和 `confidence` | 是否敏感、是否需要审核、是否应该使用道具 |

服务响应会透传 Laya 的 `model`、`answers`、`usage`，并附加 `status` 和实际 `device`。当前服务本身不解释概率、不执行动作，也不调用其他 Agent。

## 通用阈值与安全边界

可以在服务外层给每个问题定义一个简单的策略层。下面是适合开始校准的通用模式，不是模型内置逻辑：

```text
目标选项/真假概率 >= 0.90  → 自动进入对应流程
0.60 <= 概率 < 0.90        → 灰区，交给主 Agent 或人工确认
概率 < 0.60                → 走确定性默认路径或原有 fallback
```

具体取哪个字段取决于问题类型：

- `choice`：读取目标选项的 `probabilities[选项名]`；不要只看最大值而忽略目标选项。
- `noul`：读取 `noul`（问题为“是否……”时通常表示为真的概率）。
- `score`：读取目标等级在 `probabilities` 中的概率；如果业务只需要排序，也可以使用期望 `score`，但仍应设置灰区。
- `confidence`：表示模型对当前答案分布的集中程度，可作为附加门控，不应替代业务目标概率。

付款、权限授予、删除、发布、退款、掉落、封禁、法律或医疗结论等高风险动作必须由硬规则、权限校验和必要的人工确认兜底。模型概率只能决定“是否进入流程”，不能单独成为不可逆动作的授权。

建议记录模型版本、问题定义、目标概率、最终阈值动作和人工修正结果，积累真实样本后再校准阈值。当前 API 没有内置阈值策略或审计存储。

当前 `laya-multilingual` checkpoint 没有随附拟合后的温度参数，上游也明确提醒其原始概率可能过置信。因此上面的 `0.90` 只是便于讨论的起始示例，不是开箱即用的生产阈值；在自动流转前，应使用自己的中文业务验证集拟合温度并重新确定阈值。在完成校准前，更稳妥的做法是把概率仅用于排序或进入人工/主 Agent 队列。

## Agent 智能调度

在 Agent 系统中，Laya 可以先判断任务要经过哪些阶段，再由已有的主 Agent/调度层决定是否派发。一个典型流程是：

```text
用户任务
  → /v1/decide 判断任务类型、复杂度、风险和所需验证
  → 阈值策略层选择路径
  → 主 Agent/调度器派发 SubAgent
  → 汇总结果并验收
```

可使用的角色映射示例：

| 判断信号 | 可考虑的角色 | 说明 |
| --- | --- | --- |
| 需要阅读多个文件、日志或历史资料 | `evidence_researcher` | 先收集事实和证据 |
| 文件范围、方案和验收标准已明确 | `implementation_worker` | 执行已确认的独立实现 |
| 涉及 API、数据或跨组件验证 | `backend_tester` | 做后端链路和数据验证 |
| 需要真实浏览器用户链路 | `e2e_tester` | 使用真实浏览器上下文验收 |
| 存在跨系统方案和重大取舍 | `solution_designer` | 做方案设计与取舍审计 |
| 有固定基线，需要独立检查增量 | `incremental_reviewer` | 检查改动是否符合基线 |

Laya 只返回“需要什么”和“概率多大”，不会直接 `spawn_agent`，也不会替主 Agent 做需求澄清、权限决策或最终验收。低置信度、信号冲突和高风险操作应回到主 Agent/人工流程。

### Agent 调度的 Context 建议

| 场景 | 推荐 `max_len` | 输入建议 |
| --- | ---: | --- |
| 普通任务分类、角色选择 | 1,024 | 用户请求、项目类型和少量约束，通常不需要更长窗口 |
| 带结构化上下文的任务调度 | 2,048 | 请求、文件清单、错误摘要、环境和验收条件 |
| 跨系统方案判断 | 2,048–4,096 | 只放关键约束、接口摘要和冲突点，不直接附完整代码或日志 |
| 大段日志或代码调查 | 1,024–2,048 + 检索/分块 | 先由检索或主 Agent提取相关片段，再让 Laya 判断下一步角色 |

Agent 调度默认优先使用 1,024；调度器需要的是任务摘要而不是完整工作上下文。把整个仓库、完整日志或长会话塞入 4K/8K，通常只会增加延迟和噪声。

### CodeAgent 场景的实际定位

结合最近半年本地 sessions 的 443 条 blind silver-label 评测，当前原始 multilingual checkpoint 不适合一次性预测完整多 Agent 调用链：模型倾向同时选中过多角色，`p>=0.9` 的正向自动派发 Precision 仍然很低。完整数据见 [evaluation/sessions_6m/results/REPORT.md](evaluation/sessions_6m/results/REPORT.md)。

CodeAgent 中更适合的用法是“下一阶段决策”和低风险旁路信号：

- 任务粗分类：问答、调查、诊断、实现、验证或 Review。
- 判断下一步是否需要读取仓库、历史会话或外部资料。
- 判断实现完成后是否需要后端验证或真实浏览器验证。
- 根据任务摘要选择小模型/大模型、本地模型/云模型。
- 对 issue、失败日志和用户请求做模块、严重度和优先级分类。
- 对变更摘要做语义风险提示，决定是否进入独立 Review 队列。
- 以 shadow mode 记录建议路由，与主 Agent 的真实决策对比，持续收集训练数据。

不建议交给 Laya 单独决定：

- 生产、付费、删除、发布、权限提升等授权。
- 精确文件范围、代码方案和最终实现内容。
- 是否执行破坏性命令。
- 一次请求同时预测整条调查→设计→实现→验证→Review 链路。
- 使用完整仓库、完整日志或长会话作为输入。

推荐把多 Agent 调度改为 `main_control` 单点回流，而不是一次性多标签派发或让 SubAgent 直接串联：

```text
main_control
  → choice：下一步是 main_control / research / design / implement / validate / review
  → implement 或 validate 时再判断 frontend / backend / both
  → main_control 检查硬规则、确定具体 SubAgent 并派发
  → 执行结果（成功、失败或阻塞）一律回 main_control 检查
```

`research`、`design`、`implement` 和 `review` 分别对应现有的 `evidence_researcher`、`solution_designer`、`implementation_worker` 和 `incremental_reviewer`。`validate` 的前端分支对应 `e2e_tester`，后端分支对应 `backend_tester`；`both` 由 main_control 安排两项验证，不创建新角色。前后端是范围属性，不是额外状态。验证失败或 Review 发现问题时先回 main_control 归因，不硬编码为“直接再实现”。

调用方必须先给出允许的下一步；Laya 不能扩大候选范围，也不能跳过用户授权、必做检查或最终验收。当前只做 shadow mode：记录建议与主 Agent 的实际选择，不自动 `spawn_agent`。本地服务超时、不可达、返回错误或响应不合法时，本次旁路判断标记 `skipped` 及原因，原有 Codex 执行路径继续。现有 443 条角色 silver labels 不是逐阶段 next-action 金标准，不能直接拿来宣称此状态机的准确率。

## 游戏场景

### 可用方向

- NPC 的高层策略：进攻、防守、撤退、求援、交易或等待。
- AI Director：根据局面调整刷怪、资源和事件节奏。
- 动态难度：判断玩家受挫、无聊或需要提示，再由游戏规则调整参数。
- 剧情和任务分支：根据玩家行为选择下一段任务或角色反应。
- 玩家行为与运营：判断挂机、恶意聊天、流失风险、活动意向或客服升级。

推荐由游戏服务器调用，而不是让客户端直接决定或直接暴露接口。服务器还应校验返回动作是否符合角色状态、技能冷却、资源和白名单。

调用应以事件触发或批量决策为主，例如战斗阶段改变、队长阵亡、玩家进入区域或一批 NPC 统一更新；不适合在 60 FPS 的每一帧调用。移动、碰撞、技能冷却和数值约束继续由行为树、状态机或规则代码负责；服务超时、低置信度或不可用时回退到原有行为树。

### 游戏请求示例

下面的请求体可以直接作为当前 `/v1/decide` 的 JSON body：

```json
{
  "state": {

    "ammo": 3,
    "enemy_count": 5,
    "nearby_allies": 0,
    "recent_events": ["队长阵亡", "玩家正在逼近"]
  },
  "questions": {
    "action": {
      "type": "choice",
      "instructions": "NPC 下一步应该采取什么高层策略？",
      "criteria": {
        "进攻": "仍然具备明显战斗优势",
        "防守": "坚守当前位置可以等待支援",
        "撤退": "继续战斗的生存风险过高",
        "求援": "附近存在可以响应的援军"
      }
    },
    "danger": {
      "type": "score",
      "instructions": "当前战斗危险程度是多少？",

```

### 游戏场景的 Context 建议

| 场景 | 推荐 `max_len` | 输入建议 |
| --- | ---: | --- |
| NPC 高层战斗策略 | 1,024 | 当前属性、附近单位、最近事件和少量角色设定 |
| AI Director、动态难度 | 1,024–2,048 | 最近一段时间的统计摘要、玩家状态和关卡目标 |
| 玩家行为、流失或运营判断 | 1,024–2,048 | 聚合后的行为指标与最近关键事件，不上传完整行为流水 |
| 剧情或任务分支 | 2,048–4,096 | 当前章节摘要、关键选择、角色关系和任务状态 |
| 聊天安全与违规判断 | 1,024 | 当前消息加少量上下文；长聊天按窗口滚动或先摘要 |
| 大规模世界模拟 | 每个实体 1,024，批量处理 | 每个 NPC/阵营提交紧凑状态，避免单次拼接整个世界状态 |

游戏在线主链路建议默认 1,024，只有剧情和较长历史状态才提升到 2K/4K。8K 更适合低频、离线世界演算，不适合高并发实时战斗。

## 文档场景

文档通常比游戏更适合先落地：决策类型固定、吞吐可批处理，也不要求每帧级延迟。可把 Laya 放在 OCR/解析之后、业务流程之前，负责语义分流：

- 自动分类和归档：合同、发票、简历、报告、通知和申请单归类到目录、知识库或项目。
- 审批路由：判断是否交财务、法务、人事、采购或管理层。
- 外发安全：判断是否含个人信息、商业秘密、报价、账号或合同限制，决定是否脱敏、审批或拦截。
- 合同和发票初筛：判断是否需要法务/财务复核、是否疑似重复或存在高风险条款。
- 待办识别：判断文档是否包含任务、截止时间和责任人，转成待办队列。
- 知识库治理：判断内容是否重复、过期、低价值或需要更新。
- AI 工具路由：判断应该调用 OCR、表格解析、合同审查、摘要、RAG 还是人工流程。

精确字段、版面和数值一致性不要交给语义模型单独处理。例如“有没有签章”“金额是否相等”“发票号是否重复”“附件是否齐全”，应由 OCR、版面/表格解析和确定性规则完成；Laya 更适合判断“是否需要审核”“语义上是否敏感”“应该走哪条流程”。

### 文档请求示例

```json
{
  "state": {
    "filename": "供应商合作协议.docx",
    "creator": "采购部",
    "operation": "分享给外部人员",
    "content": "本协议约定供应商提供年度服务，包含付款、违约责任和自动续约条款。"
  },
  "questions": {
    "document_type": {
      "type": "choice",
      "instructions": "这是什么类型的文档？",
      "criteria": {
        "合同": "约定双方权利义务并可能需要签署",
        "报价单": "主要包含产品、数量和价格",
        "内部报告": "用于内部汇报、分析或决策",
        "其他": "不属于以上类型"
      }
    },
    "contains_sensitive_data": {
      "type": "noul",
      "instructions": "文档是否包含不适合直接对外分享的敏感信息？"
    },
    "needs_legal_review": {
      "type": "noul",
      "instructions": "文档是否应该经过法务审核？"
    },
    "risk_level": {
      "type": "score",
      "instructions": "本次对外分享的风险等级是多少？",
      "criteria": ["低风险", "需要确认", "高风险"]
    }
  }
}
```

例如外层策略可以规定：敏感概率达到阈值就阻止直接外发；法务审核概率达到阈值就进入审批；处于灰区就显示人工确认；否则继续既有分享流程。这个策略和审批执行不在当前 `/v1/decide` 内。

### 长文档处理

当前中文模型配置为 `max_len=1024`、`head_max_len=256`。问题说明和选项会占用 `head_max_len`，剩余空间才给 `state`，因此长文档不应一次性完整塞入请求。建议按章节、段落或条款切分，逐块判断后由业务层按“任一高风险即升级”、加权汇总或人工复核规则聚合。切分时保留标题、页码、文档 ID 和条款位置，方便回溯。

### 文档场景的 Context 建议

| 场景 | 推荐 `max_len` | 输入建议 |
| --- | ---: | --- |
| 文档类型识别、归档、工具路由 | 1,024 | 文件名、元数据、标题和开头/代表性片段 |
| 发票、报销单、申请单路由 | 1,024 | OCR 后的结构化字段和少量备注；精确校验仍用规则 |
| 待办、责任人、审批部门判断 | 1,024–2,048 | 相关段落、评论和流程元数据 |
| 外发安全与敏感信息判断 | 2,048 | 元数据加召回出的敏感候选段落；不要默认上传全文 |
| 合同条款风险初筛 | 2,048–4,096 | 按条款或章节处理，并保留标题、页码和条款编号 |
| 报告、制度、知识库治理 | 2,048–4,096 + 分块 | 先分章或检索相关段落，再聚合重复、过期和风险判断 |
| 超长合同或完整报告 | 分块，每块 2,048–4,096 | 不建议直接使用单个 8K 请求；逐块判断后按规则聚合 |

文档场景的默认策略可以概括为：分类路由用 1K，语义审核用 2K，章节级合同/报告分析用 4K，完整长文档使用分块而不是默认 8K。

## Context Window 与使用边界

Laya 是编码器加决策头的非生成式模型：每个问题都会把同一份 `state` 与该问题的说明/选项组合成一条输入序列；`output_tokens` 为 0，不存在聊天模型那种输入和生成输出共同增长的窗口。窗口仍受序列截断影响。

| 模型 | 默认 `max_len` | `head_max_len` | 约可留给 `state` 的空间 | 编码器理论上限 |
| --- | ---: | ---: | ---: | ---: |
| English | 512 | 192（上游文档） | 约 320 tokens | 8,192 tokens（上游配置） |
| Multilingual（当前部署） | 1,024 | 256 | 约 768 tokens | 8,192 tokens |
| Typed-Decisions | 1,024 | 256（上游文档） | 约 768 tokens | 8,192 tokens（上游配置） |

“约可留给 state”会随问题说明、选项数量和特殊 token 变化，不是硬性保证。当前服务实际按部署配置截断到 1,024；编码器支持 8,192 不等于当前模型已经按 8K 训练、校准或验证。不要仅修改配置就把 8K 当作生产承诺，应重新评估延迟、内存和准确率。

Multilingual 的 8,192 上限来自当前本地 encoder 配置；English 和 Typed-Decisions 的 8,192 来自上游 checkpoint 配置，未在本机加载实测。

### 提升 Context Window 的代价

如果保持当前 `head_max_len=256`，不同窗口大约能给 `state` 留出以下空间：

| `max_len` | 约可用于 `state` | 全局注意力部分的理论相对计算量 |
| ---: | ---: | ---: |
| 1,024 | 约 768 tokens | 1× |
| 2,048 | 约 1,792 tokens | 4× |
| 4,096 | 约 3,840 tokens | 16× |
| 8,192 | 约 7,936 tokens | 64× |

最后一列只是全局注意力中随序列长度平方增长的理论比例，不代表整个请求会严格慢相同倍数。当前 mmBERT 有 22 层，大部分层使用 128-token 局部滑窗，每 3 层才有一层全局注意力，因此总成本低于“所有层都是完整注意力”的模型，但仍会随着窗口增长而明显上升。

主要代价包括：

- **磁盘和参数内存基本不变**：权重没有变化；增加的是每次请求的激活张量和注意力工作区。
- **延迟增加、吞吐下降**：局部注意力和 MLP 部分接近随长度线性增长，全局注意力部分按长度平方增长。当前 MPS 路径使用 FP32，激活内存压力比 FP16 更高。
- **问题数量会放大成本**：Laya 会为每个问题把同一份 `state` 重新组成一条序列。长 state 配合多个 `choice`/`score`/`noul` 问题时，总 token 和批处理内存都会增加。
- **批处理更容易受最长输入拖累**：同一批次需要 padding，某个特别长的 state 会浪费其他样本的计算。
- **准确率不一定随窗口增长**：encoder 支持 8,192，不代表当前 Laya 决策头已经在 2K/4K/8K 业务输入上完成微调、温度校准和阈值验证。更长输入还可能稀释关键证据。
- **选项预算不会自动增加**：只提高 `max_len` 会扩大 state 空间，但不会解决选项过多的问题；大量 `choice` 选项还需要单独提高 `head_max_len`，这又会挤占 state 空间。
- **服务配置需要重启并重新压测**：应分别测量 P50/P95 延迟、峰值内存、并发吞吐、准确率和校准误差，不能只验证“没有报错”。

实践上建议先从 2,048 做业务验证；4,096 只用于确实需要较长上下文的请求；8,192 更适合低并发、批处理或离线分析。长文档通常仍优先采用分块、召回相关段落再决策，而不是默认把所有请求扩到 8K。

以上场景表是选型建议，不代表当前服务已经切换窗口。当前部署仍使用 `max_len=1,024`；启用 2K/4K/8K 需要修改运行配置、重启服务，并重新做延迟、内存、准确率和校准测试。

## 产品化方向

可以把当前能力包装成通用 `Decision API`：客户提交业务状态和决策问题，获得结构化答案，再由客户自己的系统执行动作。可扩展方向包括：

- 私有部署或专属模型，保留数据在客户环境内。
- 按调用量、并发量或延迟等级计费。
- 为客服、文档、游戏和 Agent 提供问题模板与行业校准。
- 保存决策日志、输入摘要、模型版本和结果，支持回放、误判分析和阈值校准。

当前本地服务只绑定 `127.0.0.1:8765`，尚未提供面向公网或多租户的产品能力。

## 生产化清单

如果把服务开放给其他机器或客户，至少需要在服务外层补齐：

- HTTPS 和 API Key/租户身份认证。
- 请求限流、并发控制、超时、重试和缓存策略。
- 模型不可用或结果低置信度时的确定性回退。
- 请求大小、文档长度和问题数量限制。
- 结构化日志、指标、告警、模型版本和决策回放。
- 敏感数据脱敏、保留期限、访问审计和权限隔离。
- 真实业务样本上的精度、校准、灰区比例和误拦截率评估。
- 高风险动作的硬规则、白名单和人工确认，不能只依赖概率阈值。

这些项目不是当前本地部署已经完成的功能；它们是服务化、商业化前的验收清单。
